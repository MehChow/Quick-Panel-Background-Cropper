# v2.0.0 persistent My Icons library handoff

Date: 2026-08-20
Target release: v2.0.0
Task size: architectural / major feature
Purpose: repository-grounded input for a later specification and
implementation-plan session

## Product intent

Add a persistent, local-only **My Icons** library so users can import personal
Button artwork once, crop it, reuse it across calibrations and customization
sessions, and delete it deliberately. This is a major v2.0.0 feature, not an
extension of the v1.5.0 Lucide catalog task.

The feature must work in both Advanced **Buttons only** and Advanced
**Controls + Buttons**. Default and Advanced Controls-only behavior must remain
unchanged.

## Why this should be a library

A durable library avoids forcing users to re-import artwork every time they
reuse a saved calibration. It also avoids coupling the lifetime of user artwork
to a calibration screenshot, an image-picker cache URI, or one Customize
session.

The core boundaries should be:

- calibration stores panel geometry, labels, order, and stable icon references;
- My Icons owns imported files and their metadata;
- Customize owns the per-session Original/Tint rendering choice;
- preview and export consume the same resolved icon source.

Do not add a separate Advanced target just for imported icons. That would
duplicate Buttons-only behavior and create a second combined-mode variant.

## Approved product decisions

- The library is persistent across app restarts and app updates.
- Imported media remains local; QPBC does not upload it.
- Initial v2.0.0 scope is album-selected raster artwork. Do not accept raw SVG
  in this release.
- The intended input scope is still PNG, JPEG, and WebP. The specification must
  verify what Android's picker actually returns and define a clear response to
  HEIC, AVIF, animated GIF/APNG, incorrect extensions, and absent MIME types.
- The custom-label icon dialog will have 24 Lucide choices after v1.5.0 and an
  **Import from album** action at the bottom-left.
- Import opens the platform image-selection panel, then a dedicated crop page.
- The crop page uses a circular viewport with the outside dimmed, supports drag
  and pinch-to-zoom, does not add rotation controls, and has Cancel and Confirm
  footer actions.
- A confirmed imported image becomes a reusable My Icons asset and is selected
  for the pending custom label.
- Imported-image chips use a distinct blue style and a small circular thumbnail
  before the label. Do not use the image as the full chip background.
- The imported image replaces the complete circular identifier badge. It does
  not render as a small glyph inside QPBC's existing light/dark badge.
- If a customization contains one or more My Icons references, ask for one
  global **Original** or **Tint** choice for that customization. The choice
  applies to every imported badge in Buttons-only or Combined.
- Ask for Original/Tint in every new Customize session; do not persist that
  choice as part of the calibration or My Icons asset.
- Original mode preserves the cropped artwork.
- Tint mode produces a monochrome image using the selected QPBC identifier
  color while retaining the artwork's luminance, contrast, alpha, and visible
  detail. It must not reduce an opaque photo to a flat colored disk.
- Built-in and Lucide custom-label icons continue using the current QPBC badge
  and icon-color behavior.

## Recommended user flow

### Import and library selection

1. The user creates a custom label from the existing Button-selection screen.
2. The icon dialog shows the 24 Lucide choices plus a My Icons area and
   **Import from album**.
3. Existing My Icons assets can be selected without reopening the album.
4. Import launches the existing system picker pattern for still images.
5. A successful pick opens the dedicated circular crop page.
6. Cancel returns without adding an asset and removes any app-owned temporary
   file created for that attempt.
7. Confirm normalizes and commits the crop into the persistent library, then
   returns to Button selection with that asset selected.
8. The selected custom-label chip uses the blue imported-image treatment and a
   small circular thumbnail.

The later specification should decide whether the dialog uses tabs
(`Library` / `Lucide`) or one scrollable surface. It must preserve the current
title, pending custom label, Cancel behavior, short-screen usability, and
accessibility.

### Reusing saved calibration

- A calibration references a stable My Icons asset ID, never an album URI,
  cache URI, absolute documents URI, or base64 payload.
- If referenced assets still exist, saved Buttons-only and Combined
  calibrations continue directly through the existing reuse flow; no
  calibration screenshot is needed.
- No `containsImportedIcons` or forced-reconfiguration flag is necessary for
  normal reuse because the library assets are durable.
- A missing or corrupt referenced asset must degrade locally and visibly; it
  must not invalidate every calibration branch or clear unrelated data.

### Per-customization mode

The current mode-selection path can skip calibration when a saved calibration
exists. Therefore, Original/Tint cannot live only after Button selection.

Recommended placement:

1. User selects Buttons-only or Combined.
2. Existing calibration is reused or a new calibration is completed.
3. User chooses the background image.
4. If the active preset contains My Icons references, show a dedicated
   Original/Tint screen before the adjustment preview.
5. If it contains none, continue directly to adjustment as today.
6. Back navigation retains the choice within the current Customize session.
7. Starting a new Customize session asks again.

The specification must define the default focus, explanatory copy, preview
sample, accessibility labels, and behavior when the user backs out before
choosing.

## Recommended feature structure

Create a focused feature boundary rather than adding file operations throughout
calibration and Customize components. A likely structure is:

```text
src/features/quick-panel/my-icons/
  components/
  hooks/
  model/
  services/
  store/
```

Responsibilities should be separated as follows:

- library model: metadata, stable IDs, schema version, validation;
- file service: temporary files, normalization, atomic commit, deletion;
- crop model: pan/zoom constraints and source-coordinate crop calculation;
- library store: list/import/delete/repair operations;
- picker and crop UI: user interaction only;
- resolver: converts a calibration icon reference into a renderable source;
- rendering adapter: shared library/Lucide/imported badge rendering for preview
  and export.

Do not put image processing or filesystem ownership rules inside the icon
dialog.

## Data-model concerns

The current model assumes every identifier is a Lucide name:

- `ButtonCalibrationItem.customIconId`
- `ButtonIdentifierDefinition.iconName`
- `getButtonIconName()`
- `ButtonIdentifierVisuals`
- `AnimatedButtonIdentifierVisuals`

The specification should replace that assumption with a discriminated union,
for example:

```ts
type ButtonIconSource =
  | { type: "lucide"; iconName: LucideIconName }
  | { type: "my-icon"; assetId: string };
```

This example is directional, not a final schema. The spec must decide:

- whether built-in labels and custom labels share one icon-source type;
- whether an imported reference stores an internal Lucide fallback;
- how a missing asset is surfaced and repaired;
- whether library assets can be used only by custom labels or also override
  built-in Button labels;
- whether duplicate custom-label text can reference different assets;
- how stable Button IDs, selection order, filenames, and rectangle ownership
  survive selection edits;
- whether the schema needs a version field before shipping v2.0.0.

Recommendation: retain a generic internal Lucide fallback such as `image` for
missing-asset rendering, show a repair warning, and keep the affected
calibration usable. Do not silently substitute a different personal asset.

## Persistent library model

Each library record should use a generated stable ID and store metadata, not
the image bytes. A likely record contains:

- stable asset ID;
- app-owned relative filename;
- normalized pixel dimensions;
- normalized format and processing version;
- creation/update timestamps if needed for ordering;
- optional original filename for user-facing diagnostics only;
- integrity or existence status derived at load time.

Do not store:

- base64 image data in MMKV;
- picker cache URIs;
- media-library asset IDs as the only reference;
- absolute sandbox paths that may change;
- the Original/Tint session choice.

Resolve relative filenames against an app-owned documents directory at runtime,
for example a dedicated `qpbc-my-icons` directory under `Paths.document`.
Confirm the exact Expo SDK 56 filesystem API in the specification.

## Atomicity and consistency

File and metadata writes span different storage systems and must be treated as
one logical transaction:

1. Pick into temporary app-owned state.
2. Validate and decode before changing the library registry.
3. Produce the normalized square crop into a temporary destination.
4. Verify the result can be loaded and has expected dimensions.
5. Move or copy it to its final documents filename.
6. Commit the metadata record.
7. Only then attach the stable asset ID to the pending Button item.

If a step fails, remove only the temporary/final file created by that attempt
and leave the previous library/calibration state intact. On startup, reconcile
orphaned app-owned files and registry entries conservatively.

Never delete the documents root, cache root, user album originals, exported
media-library copies, or files whose ownership is unknown.

## Import validation and normalization

The handoff intentionally leaves exact numeric limits for the specification,
but the spec must define all of them before implementation:

- allowed decoded formats and how format is detected when MIME/filename data is
  missing or misleading;
- animated-image rejection or first-frame policy;
- minimum useful dimensions;
- maximum long edge, decoded pixel count, and input byte size;
- handling of zero/unknown dimensions;
- orientation metadata;
- color profile and alpha handling;
- normalization size and compression;
- user-facing errors for unsupported, corrupt, or oversized assets.

Recommended starting point:

- decode common still raster images selected by the platform;
- explicitly accept the approved PNG/JPEG/WebP cases;
- reject animation for v2.0.0;
- reuse QPBC's existing large-image safety principles rather than decoding
  unbounded inputs;
- normalize the confirmed square crop to one lossless PNG, likely 512 x 512;
- clip it to a circle at render time instead of requiring transparent circular
  masking in the stored file.

The final normalization size must be derived from the largest identifier badge
in a 1024 x 1024 export, not chosen only from thumbnail requirements.

## Crop-page concerns

The crop page needs a dedicated model and tests for source-coordinate math. It
should not reuse the background image transform without checking its different
viewport and output rules.

Required behavior:

- circular viewport centered in the available preview area;
- dimmed content outside the circle;
- initial center-cover transform so the circle is always filled;
- drag to reposition;
- pinch to zoom with minimum and maximum bounds;
- no blank pixels inside the crop circle;
- no rotation control;
- Cancel and Confirm in the persistent footer;
- Android hardware Back behaves like Cancel;
- Confirm is disabled while processing;
- repeated taps cannot create duplicate assets;
- route parameters do not contain base64 or large serialized data;
- temporary selection survives normal route transitions but is cleaned after
  cancel, failure, or successful commit.

If the OS kills the activity during image selection, evaluate
`ImagePicker.getPendingResultAsync()` during the spec. Do not assume the current
background picker recovery is sufficient for a new multi-screen transaction.

## Library-management UX

The v2.0.0 scope needs a reusable management surface, not only an import button.
The specification must cover:

- empty state and Import action;
- circular thumbnails;
- loading and broken-asset states;
- selection state in the custom-label dialog;
- replace or recrop behavior;
- deletion confirmation;
- what happens when an asset is referenced by one or more saved calibrations;
- optional library-size limit and the message shown at the limit;
- accessibility labels that do not rely on thumbnails alone;
- English and Traditional Chinese copy.

Recommendation: block deletion while an asset is referenced and tell the user
which calibration targets use it. A later design may offer an explicit
"replace references with fallback" transaction, but silent reference breakage
is not acceptable.

Do not add cloud sync, sharing, folders, tags, search, bulk import, automatic
deduplication, or image editing beyond crop unless separately approved.

## Calibration and selection concerns

`ButtonPanelSelection` is shared by Buttons-only and Combined, which is the
right reuse boundary for the icon dialog and blue thumbnail chip. Preserve:

- the 30 built-in labels;
- custom-label text behavior;
- selected order;
- Buttons-only and Combined independent calibrations;
- current required Button counts and validation;
- panel rectangles and grid counts;
- the eye/area preview that depends on the calibration screenshot;
- existing amber Lucide custom-label chips and emerald built-in chips.

Add a third semantic chip state for My Icons. Use the approved blue treatment
and a small `expo-image` thumbnail. Do not use a full image background because
it harms readability and can increase decode/render work in a wrapping list.

Changing or deleting a My Icons asset must not regenerate panel rectangles or
alter Button order. Icon-source edits and geometry edits are independent.

## Original rendering mode

For an imported source in Original mode:

- render the square crop with a circular clip;
- fill the complete identifier badge;
- bypass the existing light/dark badge background for that imported badge;
- preserve source colors and alpha inside the circle;
- apply the existing overall identifier intensity consistently;
- retain existing identifier position and content-mode behavior;
- use the same crop, clip, sizing, and source in preview and export.

The label remains separate from the badge. The specification must review the
existing light/dark setting because it also influences label appearance; do not
hide or disable that control without preserving readable labels.

## Tint rendering mode: mandatory feasibility spike

This is the highest technical risk in the v2.0.0 feature.

`expo-image` `tintColor` treats every non-transparent pixel as a flat template
shape. It cannot produce the approved luminance-preserving colorization for an
opaque photo. `expo-image-manipulator` handles crop/resize/format but does not
provide a documented arbitrary color-matrix operation.

Before the implementation plan commits to a renderer, the specification phase
must run a focused technical spike comparing realistic options:

1. GPU/runtime color-matrix rendering using an already available primitive;
2. `react-native-svg` filters or masking, verified on the actual Android target
   and through `react-native-view-shot`;
3. adding a narrowly justified image-processing/rendering dependency;
4. generating and caching derived tinted bitmaps whenever the chosen identifier
   color changes.

The chosen method must prove:

- deterministic Android rendering;
- preservation of luminance, contrast, and alpha;
- live response to the existing color picker and identifier intensity;
- parity between animated preview, static preview, and captured export;
- no stale color during sequential export;
- bounded memory and cache growth;
- acceptable interaction performance with multiple imported icons;
- cleanup of any color-derived cached files.

A directional colorization rule is to preserve each pixel's luminance and alpha
while mapping its hue to the chosen QPBC identifier color. The final formula,
color space, gamma treatment, and contrast behavior must be specified and
fixture-tested.

If none of the feasible approaches survives capture/export testing, stop and
bring the product trade-off back to the user. Do not silently downgrade Tint to
flat alpha tinting.

## Preview and export integration

Current Button rendering is Lucide-specific and exists in both animated and
static paths. The implementation must update all relevant consumers, including:

- `ButtonIdentifierDefinition` and preset construction;
- `ButtonIdentifierOverlay`;
- `ButtonIdentifierVisuals`;
- `AnimatedButtonIdentifierVisuals`;
- focused appearance previews;
- main static/animated Quick Panel previews;
- `ExportSurface` and `ExportSurfaceHost`;
- Buttons-only and Combined preset builders;
- tests and fixtures that currently assume `iconName`.

Buttons preview and export must continue sharing the same panel rectangles,
original background image dimensions, image transform, intensity, label
settings, and normalized positions. Imported icon rendering must not create a
separate export-only composition.

Imported badges load asynchronously. Sequential export must wait for:

- the panel background image;
- the imported badge image or derived Tint result;
- any existing horizontal-label measurement readiness.

Readiness must remain token-scoped so callbacks from a previous panel or mode do
not release the active 1024 x 1024 capture. A badge load/processing failure must
stop the all-or-nothing export and clean only files created by that export run.

## Customize-state concerns

The Original/Tint choice is global to imported icons for one customization. It
should live in transient work state, not calibration storage or the My Icons
registry.

The specification must define:

- where the choice is reset when a new customization starts;
- how Back/forward navigation retains it within the same session;
- how it interacts with `Both`, `Icon`, and `None` identifier content modes;
- how `None` hides imported badges and disables irrelevant controls;
- how the identifier color control explains its effect in Original mode versus
  Tint mode;
- how the light/dark badge setting applies to Lucide icons and labels while an
  imported Original badge bypasses its background;
- whether changing from Tint to Original invalidates derived caches;
- behavior when a selected library asset is deleted or becomes unreadable
  while Customize is open.

Avoid adding another persisted global preference unless the user explicitly
changes the approved per-customization behavior.

## Performance concerns

- Do not store or render full-resolution album originals after normalization.
- Do not put base64 images into Zustand, MMKV, navigation params, or React keys.
- Use small `expo-image` thumbnails in grids/chips and let the full normalized
  asset load only where required.
- Bound the number and size of decoded library thumbnails on screen.
- Keep one active 1024 x 1024 export surface as the current exporter does.
- Prefetch is best-effort; it must not bypass readiness or error handling.
- Measure Tint rendering separately from Original mode.
- Test a mixed calibration containing Lucide and multiple imported icons.
- Revalidate long horizontal, long vertical, equal-span, and centered-square
  Button cases.

Any numerical performance claim requires a controlled same-device,
same-fixture, same-build comparison.

## Deletion, cleanup, and ownership

My Icons files are durable user-created app data, not stale cache. Existing
startup cache cleanup must never delete the persistent library directory.

Define separate ownership rules for:

- picker and crop temporary files under `Paths.cache`;
- committed library assets under `Paths.document`;
- derived Tint cache files;
- export cache files;
- media-library copies created by export.

Required cases:

- picker cancel;
- crop cancel;
- import/normalize failure;
- duplicate Confirm taps;
- replace/recrop success and rollback;
- delete unreferenced asset;
- attempt to delete referenced asset;
- orphaned documents file;
- registry record with missing file;
- app update and schema migration;
- app uninstall/reinstall boundary.

Cleanup must be ownership-based and limited to explicit QPBC directories or
tracked URIs. Never wipe a cache or documents root.

## Migration and backward compatibility

v2.0.0 must preserve existing user data by default:

- Default calibration;
- Advanced Controls calibration;
- Advanced Buttons calibration;
- Advanced Combined calibration;
- the original 8 and v1.5.0 expanded 24 custom Lucide IDs;
- language, help state, last exported choices, Customize settings, and release
  acknowledgement.

The storage parser should migrate existing `customIconId` values into the new
Lucide union branch without changing rectangles, labels, IDs, order, or grids.
One corrupt imported reference should invalidate or repair only that reference,
not clear every calibration branch.

Add a schema/version strategy for both calibration references and the My Icons
registry. Migration must be idempotent and tested from representative v1.4.0
and v1.5.0 persisted payloads.

## Error and recovery cases

The specification and tests must cover:

- picker unavailable, cancelled, permission-limited, or activity destroyed;
- unsupported, animated, corrupt, oversized, or zero-dimension input;
- crop transform invalid or source no longer readable;
- normalization failure;
- documents directory creation/write/move failure;
- registry write failure after file commit and the reverse ordering;
- missing/corrupt asset on startup;
- asset deleted while referenced;
- Original/Tint processing failure;
- imported image load failure in preview or export;
- stale async callbacks after navigation, replacement, or mode change;
- crash between temporary write, final file commit, and metadata commit.

User-facing errors should identify a repair action such as Retry, Re-import,
Use fallback, or Cancel. They must not expose raw sandbox paths.

## Localization, accessibility, and styling

- Add complete English and Traditional Chinese copy.
- Use existing AniUI dialogs, buttons, screen shells, and dark surfaces.
- Keep footer actions stable and outside crop-page scrolling.
- Imported-library blue is a semantic state; define one consistent accessible
  token rather than scattered one-off shades.
- Do not rely on chip color or thumbnails alone; include accessible text.
- Every library thumbnail needs a meaningful accessibility label and selected
  state.
- Crop gestures need concise instructions and non-gesture Cancel/Confirm
  controls.
- Respect reduced motion where animation is introduced.
- Use `expo-image` for raster thumbnails and badges.

## Release work

v2.0.0 should be treated as a major user-visible release. The later plan should
include:

- `app.json` semantic version and Android `versionCode` changes when release
  work is explicitly authorized;
- developer and public changelogs;
- a release announcement using a new descriptive announcement ID;
- concise explanation that My Icons remain local and persist until deleted;
- updated flow screenshots for Buttons-only and Combined after implementation;
- production manual test checklist additions;
- documentation of storage ownership and migration behavior.

The release announcement must not perform migration, clear MMKV, delete assets,
or force navigation. Migration belongs in storage/domain code.

### Library UX

- empty, populated, selected, loading, and broken states;
- import/select/replace/recrop/delete flows;
- referenced-delete protection;
- blue thumbnail chips;
- localization and accessibility.

### Customize and rendering

- Original/Tint screen appears every customization containing My Icons and is
  skipped otherwise;
- global mode applies to all imported badges only;
- Original mode preserves colors;
- Tint fixtures preserve expected luminance/detail;
- Lucide behavior remains unchanged;
- `Both`, `Icon`, and `None` behavior;
- horizontal/vertical/equal-span placement;

### Export

- imported badge readiness gates capture;
- derived Tint readiness gates capture;
- stale callbacks cannot release a later panel;
- mixed Lucide/imported sequential order and filenames remain correct;
- failure stops the run and cleans only run-owned outputs;
- final files remain original-quality 1024 x 1024 PNGs.

Run focused Jest suites throughout implementation, then the full suite,
TypeScript, lint, `git diff --check`, and an Android Expo export/build check in
proportion to the final design. Automated checks do not replace physical-device,
QuickStar, signed-artifact, backend, Play, or store QA; those remain user-owned.
